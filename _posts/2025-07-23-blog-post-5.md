In recent years, large language models (LLMs) like GPT-4, Claude, LLaMA, and DeepSeek have dominated the AI landscape. It feels like every tech company is racing to build the next biggest, smartest model—each one trying to outdo the last in size, performance, and capabilities.

But here’s a question we don’t ask often enough:  
**Do you know how much data it takes to pretrain a large language model?**

💡 *Fun fact*: GPT-3 was trained on such a massive amount of text that if a human tried to read it all, 24/7 without sleep, it would take them over 2,600 years!

And that’s just the data. What about the memory and compute cost?  
Training these behemoths can cost hundreds of millions (even billions) of dollars, not to mention the massive energy consumption. It’s clear that while LLMs are powerful, they’re not always practical; especially if you want cost-efficiency, sustainability, and real-time performance.

Now compare that to **Vicuna‑13B**, a lightweight open‑source chatbot developed by LMSYS and universities like Berkeley and Stanford. It was fine‑tuned from LLaMA using around 70,000 user-shared ChatGPT conversations and astonishingly, the entire process cost only about $300 in cloud compute. According to a GPT‑4-based evaluation, Vicuna achieves over 90% of ChatGPT/Bard’s response quality, outperforming Alpaca and LLaMA in more than 90% of cases.

This shows that we don’t always need to train or deploy massive LLMs to build capable, high-performing systems. With careful fine-tuning and efficient design, **small language models (SLMs)** can deliver impressive results often at a fraction of the cost and computational burden. While the race to build ever-larger models continues, it’s equally important that we start giving attention to small language models.

### What “3 billion parameters” actually means

When a model is described as having **~3.1B parameters**, that number is the **total count of trainable floating-point weights** in all matrices and vectors: every linear layer, convolution, bias (if present), and embedding table. Each **parameter** is one number the optimizer updates during training.

Roughly, those weights fall into a few buckets:

- **Token embeddings**: a large lookup table `vocab_size × hidden_dim` that turns each discrete token ID into a vector. This alone can be hundreds of millions of parameters for a wide hidden size and large vocabulary.
- **Per-layer transformer blocks** (stacked ~36 times in the 3B LM): for *each* layer, attention projections (query, key, value, output), feed-forward (expansion) layers, and small norm parameters. This is where most of the “depth” of the model lives.
- **Output / unembedding** (sometimes **tied** with input embeddings): maps hidden states back to logits over the vocabulary. If tied, the same weight matrix is reused for input and output, which saves parameters and is a common design choice in LLaMA-style models.
- **Vision side**: patch embedding (e.g. convolutions over patches), the vision transformer trunk, and any projection layers that map vision hidden size to the LM hidden size so visual tokens “speak the same dimension” as text tokens.

So “X billion parameters” is not one monolithic matrix; it is the **sum of every learnable tensor** across language and vision modules.

### What “non-embedding weights” means

Reports often split **total parameters** vs **non-embedding parameters**. **Embeddings** here usually means the **input token embedding table** (and sometimes the separate output projection if it is not tied). Those tables are wide and shallow: enormous width (`vocab_size`) × moderate depth (`hidden_dim`).

**Non-embedding weights** means: **everything except those large vocabulary lookup tables** in practice, almost all of the depth of the network (attention + FFN in every layer), vision encoder weights, and other adapters. That figure answers the question: “How big is the *transformer stack* itself, if we set aside the word-ID lookup sheets?” It is a useful way to compare architectures when vocabulary sizes differ.

For Qwen2.5‑VL‑3B, quoting **~3.1B total (~2.8B non-embedding)** signals that a few hundred million parameters sit in embeddings / tied structures, while **~2.8B** are in the deep residual stack that does the heavy representational work.

### Inside one decoder block (transformer layer)

A modern decoder-only block (as in Qwen2.5) is usually organized as **pre-normalization** residuals: normalize, apply a sublayer, add the residual back; repeat for attention and FFN.

1. **RMSNorm (root mean square layer norm)** on the hidden stream. Unlike LayerNorm, RMSNorm does not re-center activations; it scales them for stable magnitude before attention and FFN. There are separate norm weights for the attention branch and the FFN branch.

2. **Masked self-attention** (causal: each position may attend only to itself and previous tokens). For each position the model builds **queries**, **keys**, and **values** as linear projections of the hidden vector. Attention scores how well each query matches each key; the result is a weighted mix of values. That mix is projected again to produce the sublayer output.

3. **Grouped Query Attention (GQA)**: in full multi-head attention every head has its own K and V projections. In GQA, **many query heads share fewer key/value heads**. K/V are duplicated or grouped so **memory and bandwidth** for caching keys/values during inference drop sharply, with limited quality loss, especially important for long contexts.

4. **Rotary Positional Embeddings (RoPE)** bake relative **position** into Q and K by rotating them in embedding space instead of adding absolute position vectors. That gives good length generalization and is how the model knows token order up to very long windows (e.g. 32K in this family).

5. **Residual add**: the attention output is added back to the stream (skip connection), so gradients can flow through depth.

6. **Second RMSNorm** then **feed-forward network (FFN)**. In SwiGLU-style FFNs there are **two** linear projections into a wide inner dimension; one branch is passed through a gated SiLU (“Swish”) and multiplied element-wise with the other, then projected back down. This tends to train more smoothly than a single ReLU MLP at similar width.

7. **Another residual add** completes the block. The same pattern repeats for all layers; only the first and last layers additionally interface with embeddings and logits.

Together, **GQA + RoPE + RMSNorm + SwiGLU** is the recipe for a fast, long-context, stable decoder backbone. It is the same family of ideas used in recent open LLMs, now shared with the multimodal variant.

### Vision–language integration: how images enter the transformer

The key idea is **not** a separate small “fusion MLP” bolted on at the end. Instead:

1. **Vision encoder (ViT-style)** turns pixels into a **sequence of vectors** the same way text becomes a sequence—only the *front-end* differs. Patches (often after a **Conv3D**-style stem for video to merge frames in time) are embedded, then processed by transformer blocks that use **windowed attention** on most layers for efficiency on high resolution, and **full attention** on selected layers so information can mix globally before tokens are handed to the LM.

2. **Native resolution and dynamic token counts**: tall screenshots, wide panoramas, and short clips yield **different numbers of visual tokens** (the official diagrams illustrate token counts in the thousands for large images and variable counts for video depending on FPS sampling). The LM therefore sees a **variable-length prefix** of visual tokens followed by (or interleaved with) text tokens.

3. **Projection into LM hidden size**: vision vectors are mapped so their dimension matches the decoder’s `hidden_dim`. After that, they are **indistinguishable in shape** from text token embeddings: the decoder’s self-attention runs over **one long sequence** `[visual…, textual…]`.

4. **Causal self-attention across modalities**: once inside the decoder, later text tokens can attend to earlier visual tokens (and earlier text), implementing true **joint reasoning**. E.g. “this table cell” refers to attention weights linking a word to earlier patch tokens.

5. **Video and mRoPE**: for temporal data, the model needs both **what** appears and **when**. **Multimodal RoPE (mRoPE)** extends rotary encoding so time IDs (and spatial structure) are represented in the rotary scheme, aligning frame order with absolute time when variable FPS subsampling is used.

That is how vision is **integrated into the existing transformer**: the vision tower is a **token producer**; the LM is a **generic sequence model** over mixed token types. Bounding boxes, OCR-like layout, and chart QA are then emergent capabilities from training on multimodal data, not from a separate pipeline bolted only at inference.

## 3. Instruction Tuning & Fine‑Tuning

- **Massive Pretraining (18 trillion tokens)**
  The model absorbed a huge amount of text—far more than earlier versions to build strong language abilities. 
- **Instruction Fine-Tuning (>1 million examples)**
  It was then taught how to respond to instructions, like “Describe this image” or “Answer this question,” learning real interaction patterns.
- **Reinforcement Learning (RLHF: DPO & GRPO)**
  To sound more helpful and human-friendly, it used advanced alignment techniques called Direct Preference Optimization and GRPO.
- **Multimodal Training**:
On the multimodal side, it learns on multimodal datasets (image‑text pairs), teaching the image encoder and text decoder to work together. The training includes image-text, video-text, and audio-text, aligning the vision encoder to the LLM backbone.
- **Fusion**: Once the image is processed, the output tokens merge into the language stream, allowing seamless joint reasoning across both modalities.

## 4. Modular Architecture & Extendability

- **Separate modal encoders**: Each modality (text, image, video/audio) has its own encoder but all are integrated into a shared transformer via token embeddings.

Although the 3B variant doesn’t support audio or video, its sibling, **Qwen2.5-Omni-7B** architecture reveals its full multimodal potential. It shows how the architecture can scale:

- **Thinker–Talker split**: "Thinker" generates meaning; "Talker" handles speech generation. This separation prevents interference between modalities.
- **TMRoPE (Time-aligned Multimodal RoPE)**: Aligns audio and video frames across time, crucial for lip-sync and synchronized outputs.
- **Streaming mechanisms**: Combines block-wise encoding and sliding-window decoding to support real-time, low-latency interactions.

## Fine-Tuning Qwen2.5‑VL‑3B with LoRA on LLaVAR-2

After the architecture tour, this section grounds **what fine-tuning actually is** in this project, then narrows to **LoRA** and the concrete **data** and **metrics** we watch.

### What fine-tuning an LLM looks like and why we do it

**Pre-training** teaches a model broad statistics of language (and, here, vision) from huge, noisy corpora. The weights encode general competence; grammar, world knowledge, layout but not the exact mixture of document QA, chart reading, or UI screenshots.

**Fine-tuning** (supervised fine-tuning, SFT) continues training on a **curated dataset of input–target pairs** so the same forward pass, image → visual tokens, text → token IDs, then causal prediction nudges weights toward **task-specific behavior**. Each step is still: forward propagation, compare predictions to labels, backpropagate error, optimizer update. The difference from pre-training is scale (smaller data, fewer steps) and intent: we are **specializing** a general model instead of building one from scratch.

**Purpose** here: LLaVAR-2 is **text-rich** with charts, forms, scans, and diagrams so, we want the model to **reliably ground answers in pixels** (OCR-like reading, layout, numeric reasoning) without erasing its general chat ability. Full updates to all ~3B parameters would be costly and risk **catastrophic forgetting**; **parameter-efficient fine-tuning (PEFT)** freezes most of the network and trains only a thin set of extra parameters, which is where **LoRA** fits.

### LoRA in one precise picture

A frozen linear layer uses a weight matrix **W** (shape *d_out × d_in*). LoRA does not update **W**. It adds a **low-rank** trainable correction: multiply a thin matrix **A** (*r × d_in*) with **B** (*d_out × r*), with **r** much smaller than *d_in* and *d_out*, then add **B A** (after scaling) to the frozen map. During fine-tuning, gradients flow only through **A** and **B**. Intuitively, the large singular directions of the pretrained map stay fixed; we learn **small corrective directions** that matter for our data.

$$
W' = W + \frac{\alpha}{r}\, B A
$$

The scalar **α / r** (we use **rank r = 64**, **α = 64**, so scaling equals **1**) controls how strongly the adapter perturbs the effective linear map. **Dropout 0.05** on the adapter path is mild regularization so the adapter does not memorize quirks of a ~3k-sample split.

We attach adapters to **high-leverage linear maps**: attention **queries and values** (`q_proj`, `v_proj`) and FFN / gate paths (`gate_proj`, `fc1`, `fc2`) in both language and vision blocks. Those are where representation mixing and capacity expansion happen; adapting them gives more signal per trainable parameter than adapting only the last layer. **8-bit quantization** and **gradient checkpointing** shrink memory so a single consumer GPU can host forward activations for long multimodal sequences; a **cosine learning rate schedule** (with warmup) avoids overshooting early when adapters are random.

During training, the model feeds the image through the vision encoder and lines up those visual tokens with the chat text as one long sequence. Training still uses **next-token prediction** (same as a text-only LLM). Positions that should not train the model's padding, image placeholders, or parts of the prompt we choose to skip—get label **`IGNORE_INDEX`** so they do not add to the loss. In short: vision supplies **prefix states**; the loss teaches the model to finish the assistant reply, whether the task is a chart, an invoice, or plain text.

### Metrics we actually watch (training depth)

Fine-tuning quality is not one number; it is **whether the optimization problem is well posed** and **whether the adapter is learning stable structure**.

| Metric | What it measures (in depth) | How we use it |
| ------ | --------------------------- | -------------- |
| **Masked cross-entropy (train / eval)** | Average negative log-probability of the next token given the image and all prior tokens, averaged **only** over positions where a label exists. Masking matters: without it, padding and ignored spans dilute the loss or inject wrong gradients. | Primary curve to judge **fit** and **overfitting** (train falls while eval stalls or rises → stop or regularize). |
| **Perplexity** `exp(CE)` | Same information as CE on a log scale; interpretable as “effective branching factor” per step. | Quick sanity check: CE dropping from ~2.5 to ~1.2 nats is a large reduction in uncertainty. |
| **Gradient norm (e.g. L2 of all adapter grads)** | Scale of the update direction before clipping. Multimodal batches (long visual sequences, noisy OCR) can produce **spikes**. | We clip at **`max_norm = 0.5`**; logging every ~50 steps catches instability before NaNs. If norms are tiny for many steps, the run may be **under-learning** (LR too low or dead adapters). |
| **LoRA parameter count vs full model** | Trainable scalar count in \(A,B\) matrices only. | Confirms we are touching **tens of millions** of parameters, not billions and cheap iteration on data and hyperparameters. |

**Runtime health**: we skip steps with **NaN / Inf loss** so one bad batch does not poison weights; we optionally **scale down** very large loss spikes early in training when adapters are still random. Together, these are the **operational** metrics that justify trusting later benchmark numbers.

Later in this post we report **task metrics** (exact match on **TextVQA**, **ChartQA**, **DocVQA**) after the same LoRA setup that is where “did the loss actually buy real reading skill?” is answered.

### Custom Training Logic: `QwenVLCustomTrainer`

We implement a **custom Hugging Face `Trainer` subclass** so the details above are enforced in code, not left to defaults.

#### `compute_loss()`

* Aligns logits and labels for **causal** prediction (shifted so position \(t\) predicts token \(t+1\)).
* Applies **`IGNORE_INDEX`** so padding and non-target spans contribute **zero** loss and **zero** gradient.
* Guards empty valid-label batches and applies **loss scaling** when values explode early.
* Appends to **`loss_history`** for rolling averages (used when picking a “best” checkpoint by recent mean loss).

#### `training_step()`

* Runs forward/backward with **gradient accumulation** to mimic a larger batch without more VRAM.
* Applies **gradient clipping** (`max_norm = 0.5`) and logs **gradient norms** periodically.
* Returns a safe zero loss and skips the optimizer step when loss is **non-finite**, so long runs survive messy multimodal data.


```bash

class QwenVLCustomTrainer(Trainer):
    """Custom trainer for Qwen2.5-VL with improved loss computation"""
    
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.loss_history = []
        self.gradient_norms = []
        self.best_loss = float('inf')
        self.best_checkpoint_path = None
        
    def compute_loss(self, model, inputs, return_outputs=False, 
                     num_items_in_batch=None):
        """
        Custom loss computation with better handling for vision-language models
        """
        labels = inputs.get("labels")
        if labels is None:
            raise ValueError("Labels are required for loss computation")
            
        # Forward pass
        outputs = model(**inputs)
        logits = outputs.logits
        
        # Get valid (non-ignored) labels for loss computation
        valid_labels = labels != IGNORE_INDEX
        num_valid_tokens = valid_labels.sum().item()
        
        if num_valid_tokens == 0:
            # If no valid tokens, return zero loss
            logger.warning("No valid tokens found for loss computation")
            loss = torch.tensor(0.0, device=logits.device, requires_grad=True)
        else:
            # Shift logits and labels for causal LM
            shift_logits = logits[..., :-1, :].contiguous()
            shift_labels = labels[..., 1:].contiguous()
            
            # Flatten for loss computation
            flat_logits = shift_logits.view(-1, shift_logits.size(-1))
            flat_labels = shift_labels.view(-1)
            
            # Compute cross entropy loss with ignore index
            loss_fct = nn.CrossEntropyLoss(
                ignore_index=IGNORE_INDEX,
                reduction='mean'
            )
            loss = loss_fct(flat_logits, flat_labels)
            
            # Gradient scaling for stability
            if loss.item() > 10.0:  # If loss is too high, scale it down
                loss = loss * 0.1
                logger.warning(f"High loss detected ({loss.item():.4f}), "
                               "applying gradient scaling")
        
        # Store loss for tracking (reduced frequency)
        self.loss_history.append(loss.item())
        if len(self.loss_history) > 100:
            self.loss_history = self.loss_history[-100:]
        
        return (loss, outputs) if return_outputs else loss
    
    def training_step(self, model, inputs, num_items_in_batch=None):
        """
        Custom training step with gradient monitoring
        """
        model.train()
        
        # Forward pass and loss computation
        loss = self.compute_loss(model, inputs, 
                                 num_items_in_batch=num_items_in_batch)
        
        # Handle case where compute_loss returns tuple (loss, outputs)
        if isinstance(loss, tuple):
            loss = loss[0]
        
        # Backward pass with gradient scaling
        if self.args.gradient_accumulation_steps > 1:
            loss = loss / self.args.gradient_accumulation_steps
            
        # Check for NaN or infinite loss
        if torch.isnan(loss) or torch.isinf(loss):
            logger.warning(f"Invalid loss detected: {loss.item()}, "
                           "skipping step")
            return torch.tensor(0.0, device=loss.device, requires_grad=True)
        
        self.accelerator.backward(loss)
        
        # Apply gradient clipping
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=0.5)
        
        # Monitor gradient norms (reduced frequency)
        if self.state.global_step % 50 == 0:  # Every 50 steps instead of 10
            total_norm = 0.0
            param_count = 0
            
            for name, param in model.named_parameters():
                if param.grad is not None and param.requires_grad:
                    param_norm = param.grad.data.norm(2)
                    total_norm += param_norm.item() ** 2
                    param_count += 1
            
            if param_count > 0:
                total_norm = total_norm ** (1. / 2)
                self.gradient_norms.append(total_norm)
                
                # Keep only last 100 gradient norms
                if len(self.gradient_norms) > 100:
                    self.gradient_norms = self.gradient_norms[-100:]
                
                # Only warn if gradient norm is extremely high
                if total_norm > 5.0:
                    logger.warning(f"High gradient norm: {total_norm:.4f}")
        
        return loss.detach()
    
    def save_model(self, output_dir=None, _internal_call=False):
        """Override save_model to track best checkpoint"""
        if output_dir is None:
            output_dir = self.args.output_dir
            
        # Call parent save_model
        super().save_model(output_dir, _internal_call)
        
        # Check if this is the best checkpoint based on recent loss
        if self.loss_history:
            current_avg_loss = (sum(self.loss_history[-10:]) / 
                                len(self.loss_history[-10:]))
            if current_avg_loss < self.best_loss:
                self.best_loss = current_avg_loss
                self.best_checkpoint_path = output_dir
                logger.info(f"New best checkpoint: {output_dir} "
                            f"(loss: {current_avg_loss:.4f})")
                
                # Save best checkpoint path to file
                best_path_file = (f"{self.args.output_dir}/"
                                  "best_checkpoint_path.txt")
                with open(best_path_file, 'w') as f:
                    f.write(f"Best checkpoint path: "
                            f"{self.best_checkpoint_path}\n")
                    f.write(f"Best loss: {self.best_loss:.6f}\n")
                    f.write(f"Step: {self.state.global_step}\n")
    
    def on_save(self, args, state, control, **kwargs):
        """Called when saving checkpoint"""
        checkpoint_dir = f"{args.output_dir}/checkpoint-{state.global_step}"
        
        # Check if this is the best checkpoint
        if self.loss_history:
            current_avg_loss = (sum(self.loss_history[-10:]) / 
                                len(self.loss_history[-10:]))
            if current_avg_loss < self.best_loss:
                self.best_loss = current_avg_loss
                self.best_checkpoint_path = checkpoint_dir
                logger.info(f"New best checkpoint: {checkpoint_dir} "
                            f"(loss: {current_avg_loss:.4f})")
                
                # Save best checkpoint path to file
                best_path_file = f"{args.output_dir}/best_checkpoint_path.txt"
                with open(best_path_file, 'w') as f:
                    f.write(f"Best checkpoint path: "
                            f"{self.best_checkpoint_path}\n")
                    f.write(f"Best loss: {self.best_loss:.6f}\n")
                    f.write(f"Step: {state.global_step}\n")
    
    def log(self, logs: Dict[str, float], start_time=None):
        """
        Enhanced logging with reduced verbosity
        """
        # Add custom metrics
        if self.loss_history:
            logs["best_loss"] = self.best_loss
            
        # Call parent log method
        super().log(logs, start_time)
        
        # Reduced frequency detailed logging - only every 100 steps
        if self.state.global_step % 100 == 0:
            logger.info(f"Step {self.state.global_step}: "
                        f"Loss = {logs.get('loss', 'N/A'):.4f}, "
                        f"Best = {self.best_loss:.4f}")
            if self.best_checkpoint_path:
                logger.info(f"Best checkpoint: {self.best_checkpoint_path}")

```

### Targeting the Right Layers for LoRA

We use the helper function `find_target_linear_names()` to dynamically locate linear layers for LoRA insertion:

```python
target_modules = [
    "q_proj", "k_proj", "v_proj", "o_proj",      # attention layers
    "gate_proj", "up_proj", "down_proj",         # MLPs
    "fc1", "fc2"                                  # Vision Transformer (ViT)
]
```

These layers are most responsible for:

* Modality alignment between vision and language
* Attention fusion between tokens and image regions 
* Feature transformation and compression inside the ViT

By only training adapters in these layers, we let the model adapt to **text-heavy images** like documents and charts without losing its general capabilities.

### Loss Monitoring & Stability Techniques

Multimodal training is tricky. Bad inputs or misaligned tokens can cause loss explosions or collapse. So, we implement several safeguards:

| Mechanism                   | Purpose                                               |
| --------------------------- | ----------------------------------------------------- |
| **Cross-entropy loss**      | Core loss for token prediction                        |
| **IGNORE\_INDEX**           | Avoids loss on padding, masked tokens, or image slots |
| **Loss scaling**            | Reduces instability when loss spikes                  |
| **Gradient clipping**       | Keeps training stable under noisy gradients           |
| **Gradient norm tracking**  | Provides diagnostics every 50 steps                   |
| **Skip NaN/Inf loss steps** | Ensures training won’t crash on bad batches           |

These tools let us train reliably, even with noisy OCR spans, overlapping bounding boxes, or variable-length image tokens.

## Benchmarking Qwen2.5‑VL on TextVQA & ChartQA

To evaluate how well our fine-tuned model understands and reasons over text-rich images, we benchmarked it using two widely-used datasets from the LLaVAR-2 suite: TextVQA, ChartQA and DocVQA. These benchmarks allow us to assess a model's ability to perform OCR-based reasoning, comprehension, and visual-text alignment in real-world scenarios.


### Why These Benchmarks Matter

* **TextVQA** requires reading and reasoning over text embedded in images. It's representative of real-world scenarios like interpreting receipts, menus, or PDFs.
* **ChartQA** tests the ability to understand and reason over visualizations such as bar charts, line graphs, tables, and more.
* **DocVQA** evaluates a model’s ability to understand and extract information from visually complex documents such as invoices, forms, and reports. It requires reasoning over both textual and layout elements within scanned document images.

Both tests demand high-quality OCR, precise visual-text alignment, and robust logical reasoning.

---

| ---------- | ---- | -------------- | -------------- | ------------- |

| LLaMA‑3.1  | 8B   | 61.0           | 69.9           | 69.3          |

### Our Fine-Tuned Qwen2.5‑VL‑3B Results

After fine-tuning our **3B** model on LLaVAR-2 using LoRA (with \~3,000 samples, 3 epochs, 8-bit quantization, etc.), we evaluated on the same validation splits and got:

| Task    | Qwen2.5‑VL‑3B (Fine-Tuned) EM |
| ------- | ----------------------------- |

### What This Tells Us

1. **TextVQA**
   Our compact 3B model (**86.0%**) surpasses all previously reported small LLMs, even across 8B and 13B models and even slightly outperforms the base 7B (**84.9%**).

2. **ChartQA**
   It lands between Phi‑3 Mini (**78.5%**) and larger models like Vicuna and the 7B base, indicating strong performance given its size (**71.6%**).

3. **DocVQA**
   Achieving **78.0%**, our 3B model significantly outperforms all baseline small models (Vicuna-13B: **71.3%**, Phi-3: **66.1%**). This showcases its ability to generalize to complex document layouts despite limited training.

4. These results reinforce a key insight: smart, focused fine-tuning can allow small models to beat larger counterparts, especially on tasks aligned with their training data.
